## 0. Contexte et périmètre

Avec EPIC-08 (branche en cours de fusion), un vendeur certifié choisit une formule, signe un **mandat de test** et publie son annonce **dans Realesty uniquement** (`sales.stage = published`). L’onglet **Visites** (`/vendeur/visites`) est encore un écran « Bientôt » (`ComingSoonPage`). Il n’existe **aucune app acquéreur** (A1+ au backlog) : personne ne peut encore demander une visite depuis l’app.

**Dans le périmètre d’EPIC-09** :
- V12 : **créneaux de visite** d’une vente (formules 1 %), semaine par semaine, modèle hebdomadaire « Répéter chaque semaine », durée d’une visite ;
- V13 : **demandes de visite** (en attente / confirmées / passées), accepter, refuser, annuler, indiquer « acquéreur absent » ; onglet Visites avec plusieurs biens / lots ;
- V13b : **profil « light »** de l’acquéreur (instantané figé, jamais ses données privées) ;
- V14 : **compte rendu de visite** rédigé par l’agent (l’équipe Realesty en v1) ;
- notifications in-app (nouvelle demande, annulation, rappel la veille, compte rendu publié) ;
- fonctions `staff_*` + runbook pour **saisir les demandes, les décisions de l’agent et les comptes rendus** à la place des acquéreurs et des agences, et **données de démonstration** marquées.

**Hors périmètre** : V12b tableau de bord de vente, V15, V16, V17 (EPIC-10) ; app acquéreur (A1+), Pass Visite et score de compatibilité réels (moteur de matching), Espace Agences (P1+) ; SMS / e-mail / push ; synchronisation avec le calendrier de l’iPhone ; messagerie.

### 0.1 Ce qui fonctionne en v1 sans acquéreurs

| Fonction | En v1 | Plus tard (app acquéreur / agences) |

| Demandes de visite | **Saisies par l’équipe** (`staff_create_visit_request`, `source = staff` ou `agency`) : prospects téléphoniques, visites organisées par l’agent L’Expert ; ou **démo** (`staff_seed_demo_visits`, `source = demo`) | Créées par l’acquéreur (`source = buyer_app`, `buyer_user_id`) |

| Profil light, score, badges | Saisis par l’équipe (instantané libre mais contrôlé) ; blocs masqués s’ils sont vides | Copiés automatiquement depuis le tunnel acquéreur (A1–A5) |

Toutes les lignes saisies pendant la phase de test portent **`is_test = true`** ; les données de démonstration portent en plus `source = 'demo'` et se suppriment en une commande.

## 2. Modèle de données — migration `AAAAMMJJhhmmss_visites.sql`

Additive, `text + check`, triggers `seller_tunnel_set_updated_at`, RLS propriétaire seul, **aucune écriture directe des colonnes d’état** (RPC `security definer`, `set search_path = ''`, contrôle de `auth.uid()` et de l’état courant). Prérequis : migrations d’EPIC-08 (`sales`) et d’EPIC-11 (`pg_cron`, contrôle de format de `notifications.kind`) poussées.

Toutes les heures sont des `timestamptz` ; les règles hebdomadaires s’interprètent **à l’heure de Paris** (`at time zone 'Europe/Paris'`, changements d’heure compris). Le calcul des créneaux est fait **une seule fois, en SQL** (§2.8 `visit_week`) : l’app n’a pas de base de fuseaux horaires à embarquer ni de logique à garder en parité.

### 2.1 `sales` (extension)

| Colonne | Type / règle |
|---|---|
| `visit_duration_min` | smallint not null default 45 check in (30, 45, 60) — le battement est le reste de l’heure (Q1) |
| `visit_repeat_weekly` | boolean not null default true |
| `visit_auto_accept` | boolean not null default false — **prévu, non exposé en v1** (Q4) |

`grant update (visit_duration_min, visit_repeat_weekly)` à `authenticated` ; la politique d’EPIC-08 (« vente active ») s’applique.

### 2.2 `visit_availability` — modèle hebdomadaire

`id` uuid pk, `sale_id` → `sales` on delete cascade, `owner_id` (dénormalisé, = `sales.owner_id`, contrôlé par trigger), `weekday` smallint 1–7 (ISO, 1 = lundi), `start_minute` smallint check (`start_minute between 420 and 1200 and start_minute % 60 = 0`, soit 07:00 à 20:00), `created_at`. `unique (sale_id, weekday, start_minute)`.
- Utilisé seulement si `visit_repeat_weekly` ; conservé (mais ignoré) quand le vendeur désactive la répétition, pour pouvoir la réactiver sans tout ressaisir.
- RLS : `select` propriétaire ; écriture par `apply_visit_slot_changes` seulement.

### 2.3 `visit_slot_overrides` — exceptions datées

`id`, `sale_id`, `owner_id`, `starts_at` timestamptz (début d’heure à Paris, contrôlé par trigger), `state` check in (`open`, `closed`), `created_at`. `unique (sale_id, starts_at)`.
- Répétition active : une exception ouvre ou ferme **un seul jour** (« Seulement le samedi 3 octobre ») ; répétition inactive : chaque créneau ouvert est une exception `open`.
- Les exceptions passées sont supprimées par la tâche horaire (§3).

### 2.4 `visit_requests` — demandes de visite (prêtes pour l’app acquéreur)

| `buyer_user_id` | uuid null → `auth.users` on delete set null (**app acquéreur plus tard** ; null = saisi par l’équipe) |
| `buyer_label` | text 1–60 (« Thomas & Léa B. » : prénoms + initiale du nom, **jamais** le nom complet — règle du runbook) |

| `cancelled_by` | text null check in (`buyer`, `seller`, `agent`, `system`) |

Index et invariants :
- `unique (sale_id, slot_starts_at) where status = 'accepted'` : **un seul acquéreur par créneau** (course entre deux acceptations impossible) ;
- index `(owner_id, status, slot_starts_at)` et `(sale_id, slot_starts_at)` ;
- trigger `visit_requests_check` : vente du bon propriétaire, `owner_id` cohérent, `slot_starts_at` aligné sur la grille ; à la création, vente qui accepte des demandes (`visit_sale_accepts_requests(sale)` : `published` en EPIC-09, élargie par EPIC-10 à `under_offer`) et propriétaire non désactivé (`profiles.deactivated_at is null`).
- RLS : `select` du vendeur (`owner_id = auth.uid()`). **Aucune** politique d’écriture. La future politique acquéreur ne lira pas cette table directement : une fonction `my_visit_requests()` exposera un sous-ensemble de colonnes (§2.12), pour que les motifs de refus restent côté vendeur.

### 2.5 Instantané de l’acquéreur (`buyer_snapshot`, version 1)

Le vendeur ne lit **que** cet instantané figé, jamais une jointure vers des tables de l’acquéreur (spec §4.6, principe 4).

```json
{
  "v": 1,
  "household": "Couple, 1 enfant",
  "financing": "Validé par le courtier",
  "capacity": "Compatible avec votre prix",
  "timeline": "Achat sous 3 mois",
  "subscores": [
    { "label": "Intérieur", "score": 33, "max": 35 },
    { "label": "Extérieur & trajets", "score": 32, "max": 35 },
    { "label": "Financement", "score": 29, "max": 30 }
  ],
  "reasons": ["…", "…", "…"]
}
```

`visit_buyer_snapshot_is_valid(jsonb)` (immutable) : clés **sur liste blanche** seulement (aucune clé `phone`, `email`, `income`, `address`…), textes ≤ 80 caractères, ≤ 5 sous-scores (`0 ≤ score ≤ max ≤ 100`), ≤ 5 raisons de ≤ 160 caractères, `v = 1`. Tous les champs sont facultatifs : l’app masque chaque bloc absent.

### 2.6 `visit_reports` — comptes rendus

`id`, `visit_request_id` unique → `visit_requests` on delete cascade, `sale_id`, `owner_id`, `author_kind` check in (`agent`, `team`) (+ `buyer` avec l’app acquéreur), `author_label` ≤ 80 (« Camille, agence partenaire »), `agency_label` ≤ 80, `author_user_id` uuid null (futur compte d’agent), `interest_level` check in (`low`, `medium`, `high`), `liked` text[] (≤ 8 éléments de ≤ 120 caractères), `concerns` text[] (idem), `next_steps` text[] ⊂ (`contre_visite`, `offre_annoncee`, `reflexion`, `pas_interesse`), `comment` ≤ 1 000, `published_at`, `source` (`staff`, `agency`, `demo`), `is_test`, `created_at`, `updated_at`.
- RLS : `select` du vendeur **si `published_at` non nul** ; écriture par l’équipe seulement.

### 2.7 `visit_seller_notes` — note privée du vendeur

`visit_request_id` pk → `visit_requests` on delete cascade, `owner_id`, `note` text ≤ 500, `updated_at`. RLS : le vendeur lit / crée / modifie / supprime ses notes (politique restrictive : la demande lui appartient). Table séparée pour que la ligne `visit_requests` reste partageable avec l’acquéreur plus tard sans exposer la note.

### 2.8 RPC du vendeur (`security definer`, `authenticated`)

| Fonction | Contrôles | Effet |
|---|---|---|
| `visit_settings_defaults() returns jsonb` (immutable) | — | constantes partagées app / serveur : `min_notice_hours` 24, `horizon_weeks` 6, grille 07:00–20:00 (Q1, Q3) |
| `visit_week(p_sale_id uuid, p_monday date) returns jsonb` | vente de l’appelant, formule `essentiel` / `premium` | 7 jours × cases horaires avec leur état : `open`, `closed`, `booked` (visite acceptée), `booked_elsewhere` (visite acceptée sur une autre vente du vendeur, Q11), `pending` (ouvert avec demande(s) en attente), `past` (avant le délai de prévenance ou hors horizon) + ids des demandes liées |
| `apply_visit_slot_changes(p_sale_id uuid, p_changes jsonb) returns jsonb` | formule 1 % ; `stage in ('mandate_signed', 'published')` ; ≤ 200 changements ; cases dans la grille, futures, dans l’horizon ; une case `booked` ne se ferme pas (`slot_booked`) | chaque changement `{scope: 'weekly', weekday, start_minute, open}` ou `{scope: 'date', starts_at, open}` ; idempotent (rejouable après un délai dépassé) ; renvoie `visit_week` de la semaine touchée |
| `respond_visit_request(p_request_id uuid, p_decision text, p_reason text default null) returns void` | demande du vendeur, `handled_by = seller`, `pending`, créneau futur ; accepter : créneau libre | `accepted` ou `refused` (+ motif) ; accepter **refuse les autres demandes en attente du même créneau** (`slot_taken`, Q8) ; rejouable (même décision = sans effet) |
| `cancel_visit(p_request_id uuid, p_reason text default null) returns void` | `accepted`, créneau futur, `handled_by = seller` | `cancelled`, `cancelled_by = seller` ; l’équipe prévient l’acquéreur (runbook) |
| `set_visit_outcome(p_request_id uuid, p_outcome text) returns void` | `accepted` / `done` / `no_show`, créneau commencé, au plus 7 jours après | `done` ou `no_show` (« Acquéreur absent ») |

Erreurs typées (`P0001` + code : `sale_not_found`, `formula_not_self_managed`, `slot_booked`, `slot_outside_grid`, `slot_past`, `request_not_pending`, `slot_taken`, `too_late`) mappées en l10n.

### 2.9 Notifications

Types EPIC-09 (le contrôle de format d’EPIC-08 / EPIC-11 les accepte ; l’app lit tout type inconnu comme `other`) : `visit_requested` (« Nouvelle demande de visite · Thomas & Léa B. · sam. 3 oct. à 10 h »), `visit_cancelled` (par l’acquéreur ou l’agent), `visit_updated` (requalification faite, décision de l’agent L’Expert, visite programmée par l’agent), `visit_reminder` (la veille), `visit_report_published`. Route : `/vendeur/visites/demandes/<request id>` (compte rendu : `…/compte-rendu`). Écrites par une fonction interne `visit_notify(request, kind, title, body, screen)` (même modèle que `sale_notify`).

## 6. User stories (EPIC-09)

- **US-09.1 · Ouvrir mes créneaux de visite (V12)** — *En tant que vendeur L’Essentiel ou Premium, je veux ouvrir et fermer mes créneaux semaine par semaine.*
  - Semaine navigable jusqu’à 6 semaines, cases horaires Disponible / Réservé / Fermé avec légende ; délai de prévenance de 24 h.
  - « Répéter chaque semaine » applique mes créneaux à toutes les semaines ; « Seulement ce jour-là » crée une exception ; durée d’une visite 30 / 45 / 60 min.
  - Une case réservée ne peut pas être fermée (message) ; une visite acceptée sur un autre de mes biens bloque la case.
  - Enregistrement automatique, erreur réseau signalée sans perte de l’état serveur.
- **US-09.2 · Voir mes demandes de visite (V13)** — *En tant que vendeur, je veux voir les demandes en attente, confirmées et passées de tous mes biens en vente.*
  - Segments avec compteurs ; carte avec date, compatibilité et badges de qualification ; filtre par bien si j’en vends plusieurs.
  - Pastille sur l’onglet Visites tant qu’une demande attend ma réponse ; états vides avant publication et sans demande.
- **US-09.3 · Accepter ou refuser une visite** — *En tant que vendeur 1 %, je veux accepter ou refuser une demande.*
  - Accepter confirme la visite et refuse automatiquement les autres demandes du même créneau.
  - Refuser ouvre une feuille avec un motif facultatif, jamais transmis tel quel à l’acquéreur.
  - L’Expert : lecture seule, « Géré par votre agent ».
- **US-09.4 · Annuler une visite et indiquer son issue** — *En tant que vendeur, je veux annuler une visite confirmée et dire si l’acquéreur est venu.*
  - Annulation avec confirmation ; l’équipe prévient l’acquéreur.
  - Une visite passée est « Réalisée » par défaut ; « Acquéreur absent » possible pendant 7 jours ; note privée.
- **US-09.5 · Profil light de l’acquéreur (V13b)** — *En tant que vendeur, je veux savoir pourquoi un acquéreur est compatible sans voir ses données privées.*
  - Score et sous-scores, raisons, foyer, financement, capacité, calendrier ; mention de confidentialité ; blocs vides masqués.
- **US-09.6 · Lire le compte rendu d’une visite (V14)** — *En tant que vendeur, je veux lire le compte rendu d’une visite menée par un agent.*
  - Auteur, acquéreur, intérêt, points appréciés, freins, prochaine étape ; notification à la publication ; « Ouvrir la négociation » quand une offre existe (EPIC-10).
- **US-09.7 · Être prévenu** — notifications in-app : nouvelle demande, requalification / décision de l’agent, annulation, rappel la veille, compte rendu publié ; chacune ouvre la demande.
- **US-09.8 · Saisie par l’équipe et démonstration (avant l’app acquéreur)** — fonctions `staff_*` et runbook « Organiser les visites » : saisir une demande, requalifier, décider pour l’agent, annuler, publier un compte rendu ; démo de 3 demandes marquées `demo`, supprimable.
- **US-09.9 · Prêt pour l’app acquéreur** — *En tant qu’équipe produit, je veux que l’app acquéreur puisse se brancher sans migration de données.*
  - `buyer_user_id`, `source`, instantané versionné et contrôlé, note du vendeur séparée, calcul des créneaux côté serveur ; aucune politique ne joint les tables de l’acquéreur.

## 9. Risques

| Risque | Parade |
|---|---|
| Onglet vide sans acquéreurs : rien à tester ni à montrer | Saisie par l’équipe + démo `staff_seed_demo_visits` marquée et supprimable ; états vides soignés. |
| Données personnelles d’acquéreurs saisies à la main (nom complet, téléphone dans l’instantané) | Instantané sur liste blanche + longueurs contrôlées en SQL ; règle « prénom + initiale » dans le runbook ; coordonnées jamais stockées côté vendeur. |
| Fuseau horaire / changement d’heure (créneaux décalés d’une heure) | Un seul calcul en SQL à l’heure de Paris ; test de la semaine du changement d’heure dans la sonde. |
| Double réservation d’un créneau | Index unique partiel sur les visites acceptées + verrou de ligne dans la RPC ; refus automatique des autres demandes. |
| Pas de rappel fiable sans push | Rappel in-app via `pg_cron` + prochaine visite sur la carte « Ma vente » ; push / e-mail au backlog (Brevo, APNs). |
| Conflits de fichiers avec EPIC-08 (carte « Ma vente », V11a, routes) et EPIC-10 (V14 → V16) | VI7 après fusion d’EPIC-08 ; lien vers V16 par `isRouteAvailable` ; routes de visites groupées dans une seule fonction du routeur. |
| L’acquéreur est prévenu hors app (pas de SMS / e-mail) | Runbook : l’équipe appelle l’acquéreur à chaque décision ; dans l’app, aucune promesse d’envoi automatique. |
| Dépendance à `pg_cron` (EPIC-11) | `create extension if not exists` ; l’app déduit l’état d’un créneau passé même si la tâche n’a pas tourné. |
